# 统一编号、状态与 YAML 写法，发布《基础规范 V0.1》

## 1. 原有做法或原有判断

底座整理前，项目内同时存在多套互不兼容的做法：

- 编号体系三套并存：英文前缀（SRC-ZHUANGZI-001、PAS-ZZ-XINZHAI-001、DEC-2026-001）、中文全称（文献编号：）、混合写法；
- 状态名称三套并存：中文状态、英文状态（pending_review、active、reviewed、unsupported 等）、中英混用；
- YAML 写法两套并存：键中文值中文、键英文值英文；
- 知识卡模板只有六类，缺少争议卡、现代研究卡、风险资料卡三种模板；
- 项目总体分期的核心主题为“静、心、气、息、身”，缺少“虚”；
- 项目简介与总体分期仍使用已作废的 A—E/X 单维证据等级表。

## 2. 发现的问题

原有做法会造成以下后果：

- 同一张卡在不同文件里编号规则不一致，无法自动关联和检索；
- 状态词不统一，卡片流程无法衔接，也难以判断某张卡处于哪一环节；
- 键中英混用导致机器难以统一解析卡片；
- 缺少三种模板，对应资料没有固定记录格式；
- 主线六字“静虚心气息身”与总体分期核心主题不一致；
- 新旧两套证据等级并存，读者无法判断等级含义。

## 3. 可选方案

### 方案一：全盘重写所有已发布文件

**内容：** 直接修改所有 V0.1 文件为 V0.2，统一删除旧编号和旧状态。

**优点：** 一步到位，文件内不再存在旧写法。

**问题：** 已发布文件在 git 历史外不可追溯；改动面大，容易引入错误；违背“已发布文件可追溯”原则。

### 方案二：发布《基础规范 V0.1》作为统一口径，已发布文件逐步升级

**内容：** 新写一份《基础规范 V0.1》集中规定编号、状态、YAML 写法和模板清单；本次同步把四份规范文件升级为 V0.2 对齐新口径。

**优点：** 新旧规则有唯一权威出处；旧版本保留在 git 历史中可追溯；改动受控。

**问题：** 短期内旧文件（如暂未升级的文档）与新规范并存，需要靠升级批次逐步消化。

### 方案三：只写规范，不升级现有文件

**内容：** 只发布《基础规范 V0.1》，现有文件一律不动。

**优点：** 改动最小。

**问题：** 规范与现行文件长期不一致，规范会失去约束力，等于没有执行。

## 4. 最终决定

采用方案二，并明确执行批次：

1. 发布《基础规范 V0.1》，统一编号、状态、YAML 写法、等级口径、主线与目录；
2. 四份规范文件同步升级为 V0.2（项目章程、证据等级规范、安全边界、基础知识卡模板总纲、项目总体分期、项目简介），对齐新口径；
3. 九类知识卡模板按《基础规范 V0.1》编制，统一为 V0.2（新增争议卡、现代研究卡、风险资料卡）；
4. 第一批样板卡按新编号体系建立；
5. 本决策记录统一决定的形成过程。

## 5. 决定依据

- 底座统一检查报告（10 项问题，其中 3 项为阻断性冲突）；
- 《基础规范 V0.1》第 2—8 节；
- 项目章程第 19 节项目基本声明（允许修改、持续修正）；
- git 历史保留旧版本，保证可追溯。

## 6. 反对意见

- 有意见认为应一次性重写全部文件（方案一），理由是短期更干净；
- 未采纳原因：重写已发布文件会破坏追溯性，且一次改动过大难以核对；
- 已接受部分意见：本次同步升级的规范文件多于原计划，减少新旧并存的过渡期。
